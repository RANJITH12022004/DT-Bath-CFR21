# ESP Command Spec — Friability Tester (friability_firmware.txt)

Serial ASCII protocol between the Raspberry Pi (Friability kiosk backend) and the ESP motor controller.
Firmware team should implement command parsing and reply formats exactly as specified.

## Transport / framing

- **Pi -> ESP commands** are ASCII strings terminated by:
  - `*` (command terminator)
  - newline (`\n`)
- **ESP -> Pi replies** are ASCII lines terminated by newline (`\n`)
- Replies are newline-delimited; do not merge multiple reply lines into one line.

## Design summary

- **No** drum/holder pre-check.
- Pi sends `start,<rpm>*` for test runs or `val,<rpm>*` for validation.
- Pi sends `pause*` / `resume*` for pause and resume (count continues on resume).
- Pi sends `stop*` when the run ends or the user aborts.
- Pi sends `dispense*` for auto-dispense (reverse drum).
- Pi owns all timing (USP 4 min, custom time, or count-derived duration).

## Command set

### 1) Start mode (test) with pause/resume

**Start command (Pi -> ESP):**

```text
start,<rpm>*
```

- `<rpm>`: integer motor speed, **20–70** RPM.

**Expected replies (ESP -> Pi):**

1. Immediate ack:

   ```text
   ok
   ```

2. Stream progress (one per revolution):

   ```text
   1
   2
   3
   ...
   ```

**Pause (Pi -> ESP):**

```text
pause*
```

**ESP -> Pi:**

```text
ok
```

(No further count lines while paused — motor stopped.)

**Resume (Pi -> ESP):**

```text
resume*
```

**ESP -> Pi:**

```text
ok
4
5
6
...
```

(Continues from last count — do not reset to 1.)

**Stop (Pi -> ESP):**

```text
stop*
```

**ESP -> Pi:**

```text
ok
```

### 2) VAL mode (validation) with pause/resume

**Start command (Pi -> ESP):**

```text
val,<rpm>*
```

Example: `val,25*`

**Expected replies (ESP -> Pi):**

1. ```text
   ok
   ```

2. Stream progress with count and RPM:

   ```text
   0,--
   1,--
   2,--
   3,--
   5,24.56
   8,25.12
   10,24.89
   ```

   - First field: rotation count (integer).
   - Second field: measured RPM (`--` while motor is spinning up / recalculating, then decimal RPM when stable).

**Pause / Resume / Stop:** same as Start mode (`pause*`, `resume*`, `stop*` → `ok`).

On resume after pause, RPM resets to `--` until recalculated:

```text
resume*
ok
10,--
11,--
12,--
14,24.78
17,25.05
```

### 3) Dispense (reverse drum)

**Command (Pi -> ESP):**

```text
dispense*
```

**Expected replies (ESP -> Pi):**

```text
ok
1
2
3
complete
```

(`complete` or `complete.` accepted by Pi.)

```text

```

## Error behavior (ESP -> Pi)

- `error` — generic failure
- `error:motor_already_running` — start/val received while motor is running
- `error:invalid_rpm` — RPM out of range
- `error:motor_not_running` — pause/resume/stop when idle (Pi may treat as success on stop/pause edge cases)

## Firmware implementation checklist

- UART: **9600** baud (default; match `ESP_BAUD` in kiosk config).
- Parse `start,<rpm>*`, `val,<rpm>*`, `pause*`, `resume*`, `stop*`, `dispense*`.
- Validate RPM 20–70 for start/val.
- Reply `ok` to all command acks (including stop).
- Stream plain integers in start mode; `count,rpm` lines in val mode.
- On resume, continue count from last value (do not reset).
- Dispense: reply `ok`, stream counts, then `complete`.
- No USP1/USP2 adapter GPIO handling required for Friability.
